⚠ Overall Verdict

The codebase shows genuine ambition — the architecture diagram, streaming pipeline, billing metering, RLS policies, CI/CD workflows — these are not beginner work. But the gap between what's built and what's working is wide enough to sink the product in production. The "multi-model" value proposition is entirely fictional beyond OpenAI. The rate limiter is a serverless time bomb. There are two competing state architectures that neither team member seems to have resolved. Legacy files are committed. The model catalog lists models that don't exist. This is the kind of code that demos beautifully and fails silently in the real world.

The fundamental problem: junior developers often build the shape of production systems without validating whether the core mechanisms actually work under load, at scale, or across the advertised feature surface. Every one of the critical issues below falls into this category.

🔴 Critical Issues — Production-Breaking

CRITICAL In-memory rate limiter breaks entirely on serverless/multi-instance deployments lib/rateLimit.ts:55–58

The rate limiter uses new Map<string, RateLimitEntry>() and new Map<string, ConcurrencyEntry>() as its backing store. The file even documents this limitation: "Uses in-memory storage (for single-instance deployments)". The problem is this app is deployed on Vercel, which runs serverless functions. Every incoming request may hit a different cold-started instance. The maps are empty on every new instance, so the rate limiter provides zero protection in production. A user can simply hammer the API from parallel tabs and rack up unlimited LLM costs. 

// Current — every serverless instance has its own empty map
const rateLimitStore = new Map<string, RateLimitEntry>();
const concurrencyStore = new Map<string, ConcurrencyEntry>();

// Fix — use Upstash Redis (edge-compatible, serverless-safe)
import { Ratelimit } from "@upstash/ratelimit";
import { Redis } from "@upstash/redis";
const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(20, "60 s"),
});

Impact: Unlimited API spend exposure. A single bad actor or accidental client-side loop can drain the OpenAI API budget to zero with no effective server-side brake.

CRITICAL The "multi-model" core feature is entirely fictional beyond OpenAI lib/api/openai.ts · lib/modelCatalog.ts

The product is named Multi-Model AI. The README lists GPT-4o, Claude, Gemini, Grok as features. The model catalog has 20 models across 5 providers. Users can select Gemini 3 Pro or Claude Opus 4.1 in the UI. None of them work. Every model request — regardless of which model is selected — is routed through lib/api/openai.ts and hits OpenAI's API. If an unrecognized model ID comes in, getOpenAIModelName() silently falls back to gpt-4o-mini. 

// lib/api/openai.ts — silent fallback on unknown model
export function getOpenAIModelName(modelId: string): string {
  return MODEL_MAP[modelId] || "gpt-4o-mini"; // Claude/Gemini → gpt-4o-mini
}

Users selecting Claude or Gemini believe they're comparing model outputs. They're actually comparing the same OpenAI model against itself. This is not a roadmap item — it is the entire product premise. Shipping this to real users is misleading.

CRITICAL Model catalog lists models that do not exist lib/modelCatalog.ts:44–90, lib/api/openai.ts:44–52

The catalog includes openai/gpt-5.2, openai/gpt-5.2-codex, openai/gpt-5-mini, openai/gpt-5.1, google/gemini-3-pro-preview, google/gemini-3-flash-preview, xai/grok-4 — models labeled as "new" that are aspirational, not real. The billing table in supabaseService.ts also prices these non-existent models. There is even this in openai.ts: 

"openai/gpt-5.1": "gpt-5.2", // Legacy alias

A "legacy alias" to a model that doesn't exist yet. The model catalog is pure UI theater. Any actual API call for these models would fail at the OpenAI API layer, and the fallback to gpt-4o-mini means users have no idea their selected model wasn't called.

🟠 High Severity — Architecture & Security

HIGH Two competing state architectures with a compatibility shim on top lib/stores/ vs lib/state/ vs lib/store.ts

There are three separate state layers in this codebase:

• lib/stores/ — the "new" split stores: conversationStore, modelStore, settingsStore, streamStore, workspaceStore

• lib/state/ — a second set of stores: sessionStore, settingsStore, userStore (separate from the first settingsStore)

• lib/store.ts — a backwards-compatibility wrapper described in the docs as "mirrors the old useChatStore API to support gradual migration"

There is now a settingsStore in both lib/stores/ and lib/state/ that store different things with different keys. This creates confusion about which store governs which concern, potential subtle state divergence, and makes onboarding a new developer a cognitive nightmare. The "gradual migration" described in the docs has apparently been ongoing without completion.

HIGH Token estimation via character count is inaccurate and affects billing app/api/chat/route.ts:48–56, lib/hooks/useChatActions.ts

Token cost metering uses Math.ceil(message.content.length / 4) — a rough heuristic that assumes 4 characters per token. This is deeply inaccurate in practice: 

// English prose: ~4 chars/token ✓ (acceptable)
// Code (dense syntax): often 1–2 chars/token → 2–4x undercount
// CJK/Arabic characters: 1–3 chars per token → 3x undercount
// JSON/XML with whitespace: often 6–8 chars/token → overcounting

The API route itself notes: "useChatActions estimates token usage by character count (~4 chars per token)" acknowledging this is an estimate. But this estimate directly feeds into the credit hold system via estimatedPromptTokens, meaning non-English users and developers sharing code will be systematically misstated. The fix is a lightweight tokenizer like gpt-tokenizer (browser/edge compatible, zero native deps).

HIGH Rate limit bypass via email is exploitable if email is mutable lib/testerAccess.ts · lib/rateLimit.ts:269–285

The checkStreamPermission function checks isUnlimitedTesterEmail(context?.email) — if the email matches a configured tester email, all rate limits are bypassed and streams are granted Number.MAX_SAFE_INTEGER slots. The email is sourced from JWT claims in the API route: 

const sessionEmail = typeof claims.email === "string" ? claims.email : null;
// then passed straight to checkStreamPermission → isUnlimitedTesterEmail

If any of the tester emails listed in UNLIMITED_TESTER_EMAILS env var correspond to accounts whose email addresses could be changed, or if Supabase's email confirmation is bypassed, this becomes an unlimited-spend exploit. Tester bypass logic should use immutable user IDs, not mutable email strings.

HIGH No transactional integrity on multi-step DB writes inside the stream app/api/chat/route.ts:384–395, 453–468

The streaming API route performs multiple sequential Supabase writes with no transaction wrapping: first upsert to model_runs with status "running", then update on completion with tokens, cost, and output text. If the process crashes between these two writes (which is likely in a serverless environment with 5-minute stream windows), you get orphaned "running" records that never settle. The billing finalizeMetering also writes separately. Three async DB operations in a stream callback with no rollback semantics.

This leads to ghost "running" rows in model_runs accumulating over time, inaccurate usage dashboards, and potential double-charges on retries.

HIGH Authentication documentation is self-contradictory — points to implementation confusion README.md vs TECHNICAL_DOCUMENTATION.md

README.md (the public-facing doc) says: "Auth: Supabase Auth (magic link)". TECHNICAL_DOCUMENTATION.md says: "Demo authentication with NextAuth Credentials + middleware protection" and lists AUTH_SECRET (NextAuth env var) as a required production variable. The actual code uses Supabase Auth (lib/supabase/middleware.ts, createSupabaseServerClient). There is a lib/auth.ts (NextAuth config) also present.

This isn't just a docs problem — it signals the authentication system was rewritten mid-development (from NextAuth to Supabase) and the migration was never fully committed to. There are likely dead code paths around the old NextAuth config and route handlers.

🟡 Medium Severity — Code Quality & Technical Debt

MEDIUM Legacy files committed to production: store.old.ts and mockStream.ts lib/store.old.ts · lib/mockStream.ts

lib/store.old.ts is the original monolithic Zustand store, importing from ./mockStream — a mock streaming implementation. Both files are committed to the main codebase and referenced in TECHNICAL_DOCUMENTATION: "Legacy mock streaming flow retained for reference." Reference material belongs in git history or a private branch, not in the production file tree. These files add dead import paths, inflate bundle analysis, and confuse navigation. They should have been removed the moment the migration to split stores was complete.

MEDIUM Billing price tables hard-coded for fictional model IDs lib/billing/supabaseService.ts:52+

The MODEL_RETAIL_CENTS_PER_1M object prices openai/gpt-5.2, openai/gpt-5.2-codex, openai/gpt-5-mini, openai/gpt-5.1 — models that don't exist on OpenAI's API. This billing table is quietly being used to calculate real credits/holds against user accounts for models that will fall back to gpt-4o-mini. Depending on which fictional model the user selected, they could be over- or under-charged relative to the model actually called.

MEDIUM Analytics and usage tracking use localStorage — volatile, not queryable lib/analytics/usage.ts · TECHNICAL_DOCUMENTATION.md

The analytics system persists usage data to localStorage. This data is: lost when the user clears browser storage, invisible to server-side dashboards, unavailable for cross-device sessions, not aggregatable for business metrics, and silently unavailable in incognito/private browsing. The proper approach is server-side persistence to Supabase (already available). The infrastructure exists — the analytics layer just isn't using it.

MEDIUM Sources and disagreements UI is wired but never populated components/SourcesDialog.tsx · components/DisagreementsDialog.tsx

The TECHNICAL_DOCUMENTATION explicitly states: "Sources/disagreements are modeled in types and UI but not generated by the live API." There are complete UI dialogs, type definitions, and state model for these features. Users can presumably open the dialogs and see empty states — or the dialogs are hidden behind conditions that never resolve to true. Either way, this is dead feature surface shipped to production. Features that don't work should not have visible UI entry points.

MEDIUM Collaboration modes (Ensemble, Debate, Expert) use client-side synthesis with no real backend TECHNICAL_DOCUMENTATION.md — "ensemble/debate modes, a placeholder unified response is generated client-side"

Four of the seven advertised collaboration modes — Ensemble, Expert, Debate, Simulation — generate their "unified response" or synthesis client-side as a placeholder. This means the differentiated modes that justify the product's value proposition are stubs. Users in Debate mode are not watching Claude and Grok argue; they're watching a client-generated placeholder that looks like output. Combined with the fact that only OpenAI actually streams, the product's feature differentiation is largely cosmetic.

MEDIUM No input sanitization or message content validation in the chat route app/api/chat/route.ts:173–179

The API validates that messages is a non-empty array, but performs no validation on individual message content: no max-length check per message, no total-context-length guard, no character type sanitization. A client could send messages with 200K characters each (well above any model's context window), causing either upstream API errors that leak into logs, or extremely high token bills. The estimatePromptTokensFromMessages function runs but its output is only used for billing estimation — it does not gate the request.

🔵 Enhancement Opportunities — Strategic Improvements

1. Unified Provider Abstraction Layer

🎯 Core Feature Unlock ⏱ ~2 weeks

Replace the OpenAI-only client with a provider interface. Implement adapters for Anthropic SDK (@anthropic-ai/sdk), Google Generative AI (@google/generative-ai), and xAI. The chat route should resolve the correct adapter from model ID prefix, not silently default to OpenAI. 

interface ProviderAdapter {
  stream(opts: StreamOptions): AsyncGenerator<StreamEvent>;
}
// registry["anthropic"] → AnthropicAdapter
// registry["google"]    → GoogleAdapter

2. Upstash Redis Rate Limiting

🔥 Critical Fix First ⏱ ~2 days

Replace the in-memory Maps with @upstash/ratelimit. This is edge-compatible, serverless-safe, and free up to 10K requests/day. Single dependency swap, no architecture change required. Use sliding window algorithm to prevent burst-at-window-boundary exploits that fixed window allows.

  • Sliding window: no cliff-edge reset exploits
  • Atomic check-and-consume: no TOCTOU race
  • Persists across Vercel cold starts

3. Proper Tokenization (gpt-tokenizer)

💰 Billing Accuracy ⏱ ~1 day

Replace content.length / 4 with gpt-tokenizer — a pure-JS cl100k/o200k encoder, browser and edge compatible, zero native deps. Accurate within ±1 token for pre-flight estimation. For non-OpenAI models, use actual token counts returned in API responses rather than estimates. 

import { encode } from "gpt-tokenizer";
const tokens = encode(content).length; // exact
// vs Math.ceil(content.length / 4)   // wrong

4. Consolidate State Architecture

🏗 Developer Velocity ⏱ ~3 days

Delete lib/store.old.ts and lib/mockStream.ts. Merge lib/state/settingsStore into lib/stores/settingsStore (they govern different concerns but the split is confusing). Remove the compat wrapper lib/store.ts by completing the migration. One store directory, clear ownership, no shims.

  • Remove 2 dead files from production bundle
  • Single lib/stores/ as canonical truth
  • Rename lib/state/settingsStore → lib/stores/appSettingsStore

5. Message Content Guardrails

🛡 Security & Cost ⏱ ~1 day

Add server-side validation in the chat route: max message count (e.g., 100 messages), max individual message length (e.g., 32K chars), total context budget per request. Return structured 400 errors instead of letting oversized requests hit the upstream API and fail expensively. 

const MAX_MESSAGES = 100;
const MAX_MESSAGE_CHARS = 32_000;
const MAX_TOTAL_CHARS = 500_000;

6. Implement Real Collaboration Modes

🎯 Product Differentiation ⏱ ~1–2 weeks

The mode pipeline should be server-side, not client-side placeholders. For Ensemble: stream all model responses in parallel, then call a synthesis model with those responses as context. For Debate: assign explicit roles per model ID in the system prompt. For Expert: chain a review call after the initial response. These are all achievable with the existing streaming infrastructure.

7. Server-Side Analytics via Supabase

📊 Business Intelligence ⏱ ~2 days

Move lib/analytics/usage.ts from localStorage to a Supabase write on each run completion. The model_runs table already records token counts and cost — it just needs an analytics query layer on top. This unlocks cross-device usage dashboards, retention metrics, and model popularity data that is currently invisible.

8. Real Stripe Integration

💵 Revenue Enablement ⏱ ~1 week

The billing infrastructure is impressive — plans, quotas, credit ledger, hold/settle/refund. The webhook handler and checkout routes exist. Stripe is in package.json. The only missing piece is a real Stripe publishable key and price IDs. This is 80% done. The remaining 20% is connecting real price objects to the subscription flow and validating the webhook signing secret in production.
